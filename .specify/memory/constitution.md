# ハッカソンMVP 開発原則

## 基本原則

1. **仕様を先に書く**: 実装前に対象ユーザー、解決する課題、ユーザーストーリー、受け入れ条件をspec.mdに記録する。重要な未確定事項を事実として扱わない。
2. **最小の価値を完成させる**: P1のユーザー体験を端から端まで動かすことを優先する。追加機能は締切とデモへの寄与で判断する。
3. **仕様と実装を一致させる**: 技術選定と理由はplan.md、実装作業と完了状況はtasks.mdに記録し、変更時は対応する文書も更新する。
4. **受け入れ条件で検証する**: 主要フロー、入力エラー、外部サービス失敗を必要に応じて検証する。未実施のテストを成功と報告しない。デモの起動・操作手順を残す。
5. **単純で安全な構成にする**: 不要な抽象化や依存を避ける。秘密情報はコミットせず、サンプルデータと実データを区別する。認証やデータ共有が必要ならアクセス制御を仕様化する。

## 進め方

仕様 → 不明点の解消 → 技術計画 → タスク分解 → 実装 → 仕様との照合・検証。
通常の可逆な作業は継続して進め、製品の目的や必須要件を左右する不明点はユーザーに質問する。
技術スタック、公開先、AI機能の有無は製品要件から決める。

## 管理

ユーザーの指示を優先する。原則の変更時は理由と版を更新する。
初期版はハッカソン向けの暫定原則であり、具体的な応募条件・締切が判明したら調整する。
